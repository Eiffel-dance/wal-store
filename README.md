# WAL Store

A dependency-free Python reference implementation for storage, crash-recovery, key-value-store.

Run with: python3 demo.py
Tests: python3 -m unittest discover -s tests -v

## Scope

实现单写者预写日志键值存储：每次修改先写入日志，显式提交推进持久序号；进程在任意时刻被终止后，恢复出的状态必须恰好等于最后一次提交的状态。恢复输出、序号单调性、未提交记录和损坏日志拒绝行为都要稳定可测，不引入复制、压缩或外部服务。

进程在单条记录写入中途被终止时，日志末尾会留下残片（截断的 UTF-8 字节、缺少闭合结构的 JSON 前缀，或缺少记录终止符的完整记录字节）。记录终止符是一条记录可被恢复采用的边界：末尾缺少终止符的片段一律视为未完成写入被丢弃——不计入 pending_count、不推进序号、不影响查询。末尾之外的无效 UTF-8/JSON、空记录、字段或序号不合法的记录、非标准 JSON 常量和重复字段仍一律抛出 WalCorruptionError；无终止符但无法识别为一条完整合法记录的片段同样如此。恢复后的追加会先截掉残片，合法日志的字节内容不被改写。

`audit()` 提供只读日志审计入口，把可接受的边界和末尾片段暴露给调用方，不改变任何入口的结果。它严格按照 recover 的 UTF-8、JSON、字段集合、序号连续性和记录终止符规则解析日志，但不采纳重放结果：只返回 `state`、`commit_seq`、`pending_count`（三者与 recover 完全一致，state 为独立深拷贝）以及 `valid_bytes`、`committed_bytes`、`tail_bytes` 三个字节字段。`valid_bytes` 是从文件开头到最后一个带终止符且被接受的记录末尾的字节数，包含已提交前缀和未提交的 set/delete 记录；`committed_bytes` 是最后一个 commit 记录末尾的字节偏移，没有 commit 记录时为零；`tail_bytes` 等于文件字节数减 `valid_bytes`，只表示末尾未完成的写入片段。空文件或不存在的日志返回空 state、序号与待处理数均为零、三个字节字段均为零。末尾缺少终止符的片段，只有在可判定为未完成 JSON 前缀，或为通过结构、字段和序号校验的完整记录时才计入 `tail_bytes`；它不会被应用、计入 `pending_count` 或推进 `commit_seq`，截断的 UTF-8 字节也仅作为片段统计。完整记录之后出现空行、尾随空白、非法 UTF-8、非标准 JSON 常量、重复字段、错误字段集合、序号断裂或其他无法识别的非未完成内容时，audit 统一抛出 WalCorruptionError，不返回部分结果，也不替换当前内存状态。audit 不截断、不重写、不追加日志，不改变 state、commit_seq、文件大小或后续 append 行为；对同一日志前缀重复调用以及重新打开实例后结果一致。

`repair_tail()` 提供运维主动清理日志末尾未完成写入片段的入口：先按 recover/audit 完全相同的 UTF-8、JSON、记录字段、序号连续性、终止符与重复字段规则校验整个日志（任何无法证明为单个末尾未完成片段的内容——空行、尾随空白、非法 UTF-8、非标准 JSON 常量、重复字段、字段集合错误、序号跳变、未知操作等——一律抛出 WalCorruptionError，文件、内存 state 与 commit_seq 均不变），只有末尾确实存在未完成片段时才将日志就地截断到 audit 报告的 `valid_bytes`：此前任何字节不被改写，已经完整写入（带终止符）的 set/delete 记录——包括未提交的——不会被删除，仍保持 pending 并继续遵循 rollback 语义。截断经 flush 与 fsync 持久化后才采纳重放结果；打开、截断或持久化失败传播 OSError 且不改变内存提交状态。返回 `state`（清理后可重放状态的独立深拷贝）、`commit_seq`、`pending_count` 和 `removed_bytes`（本次从文件末尾移除的原始 tail 字节数）。清理成功后重新打开同一路径，恢复结果与清理前 recover() 对可接受前缀的结果完全一致，尾部片段不再出现；没有文件、空文件或没有尾部片段时 `removed_bytes` 为零且不创建文件。

`snapshot(target_seq=None)` 提供按已提交序号读取历史快照的只读入口：先按恢复规则完整解析当前日志（任何损坏统一抛出 WalCorruptionError，不返回部分快照），再重放截至目标提交的批次。省略 target_seq 时取最新提交，传 0 返回空状态；其他值必须是非布尔的非负整数且不大于最新提交序号，否则抛出 ValueError。目标之后的已提交批次和未提交尾部记录都不会出现在结果中。返回值只含 `state` 和 `commit_seq` 两个字段，state 是独立深拷贝，调用方修改不影响存储；同一日志和目标反复调用结果一致。snapshot 不追加、截断或重排日志，也不改变公开的 state、commit_seq。

`history(since_seq=0, until_seq=None)` 提供按持久序号导出已提交修改批次的只读入口，作为恢复与快照之外的历史变更视图。先校验参数形式：since_seq 必须是非布尔的非负整数，until_seq 提供时（None 表示最新提交序号）同样必须是非布尔的非负整数且满足 since_seq <= until_seq；类型错误、负数或区间倒置统一抛出 ValueError。随后按 recover 完全相同的规则完整校验日志（UTF-8、JSON、字段集合、重复字段、序号连续性、终止符与 JSON 值），末尾可判定为中断写入的片段按 recover 规则忽略，已写入但未提交的 set/delete 只留在日志中；其他损坏统一抛出 WalCorruptionError，不返回部分结果。解析得出最新提交序号后，since_seq 大于最新序号或 until_seq 超过最新序号也统一抛出 ValueError；不存在或空日志的默认调用返回空数组。返回按提交顺序排列的数组，仅纳入 since_seq < commit_seq <= until_seq 的提交，每项为 `{"commit_seq": seq, "changes": [...]}`：changes 保留该批次日志中的写入顺序，set 项含 op、key、value，delete 项含 op、key，空提交返回空 changes。返回对象及嵌套值都是独立深拷贝，调用方修改不影响存储；history 不追加、截断、重排或改写日志，不改变公开的 state、commit_seq、pending_count 或现有入口行为，同一日志前缀反复调用和重新打开实例后结果一致。

`diff(from_seq, to_seq)` 提供比较两个已提交序号状态差异的只读入口：from_seq 表示基线提交状态，to_seq 表示目标状态，序号 0 在任一侧都表示空对象。两个参数都必须是非布尔的非负整数且满足 from_seq <= to_seq，类型错误、负数或区间倒置统一抛出 ValueError，且全部形式校验先于任何日志读取完成；已关闭实例优先抛出 WalClosedError。随后按 recover 完全相同的规则完整校验日志（UTF-8、JSON、字段集合、重复字段、序号连续性、终止符与 JSON 值），任何损坏统一抛出 WalCorruptionError，不返回部分结果；可识别为中断写入的末尾片段按 recover 规则忽略，已完整写入但未提交的 set/delete 不进入差异。解析得出最新提交序号后，任一序号超过它也统一抛出 ValueError，因此不存在或空日志仅允许 diff(0, 0)。返回对象含 `from_seq`、`to_seq` 和 `changes`：changes 只保留从基线变为目标所需的键级修改，每个键最多一项，按 Unicode 码点升序排列——目标新增或值不同（按 JSON 类型区分比较，1 与 true、嵌套结构中的数字与布尔都不视为相同）的键为含 op、key、value 的 set，目标缺失的键为含 op、key 的 delete；两个状态完全相同返回空数组。返回对象及 value 的嵌套内容都是独立深拷贝，调用方修改结果不影响存储、后续提交或重复调用。diff 是纯只读观察：不追加、截断、重排或改写日志，不创建不存在的日志文件，不改变 state、commit_seq、pending_count 或下一次 append 依赖的已接受前缀边界（观测性重放后恢复缓存的边界，与 audit、scan、pending_changes 一致）；readonly 实例无需写租约即可调用，exclusive 实例调用后租约与写入能力不变，调用后现有写入、恢复和查询入口行为保持不变，同一可接受日志前缀重复调用及重新打开后结果一致，旧格式日志仍按原有恢复和异常规则工作。

`pending_changes()` 提供只读入口，查看最后一次完整提交之后、已完整写入日志但尚未进入持久状态的待处理批次，便于调用方在决定提交或回滚前检查。按 recover 的全部规则把日志解析到可接受边界：校验 UTF-8、JSON 对象、重复字段、各操作的字段集合、正整数序号、序号连续性、键和值类型以及记录终止符。末尾能够证明是中断写入的 JSON 前缀、无终止符的完整记录或截断 UTF-8 字节，沿用 recover 的丢弃规则，不计入结果；已经完整写入（带终止符）的 set 和 delete 记录即使没有 commit 也按日志顺序保留。任何超出可丢弃末尾片段范围的非法 UTF-8、非标准 JSON 常量、空记录、重复键、错误字段、未知操作、序号跳变或类型不合法，都统一抛出 WalCorruptionError，不返回部分结果，也不改变 state、commit_seq，不截断或追加文件。返回 RecoveryResult，含 `commit_seq`（最后一次完整 commit 的序号，没有时为 0）、`pending_count`（恒等于 changes 长度）和 `changes`；没有待处理记录时分别返回当前序号、零和空数组。changes 中 set 项保留 op、key、value，delete 项保留 op、key（不暴露 seq），所有嵌套值都是独立深拷贝。该入口不追加、截断或重写日志，不让查询看到未提交修改，不消耗序号；调用方修改返回对象后，存储、后续 commit、rollback、重新打开及重复调用的结果仍保持一致，audit、history、snapshot 与 repair_tail 的可观察行为不变。

`scan(start_key=None, end_key=None, limit=None)` 提供面向查询的确定性范围扫描入口：在不改变提交语义的前提下，按键范围读取最后一次完整 commit 的视图。起始键包含在结果中（闭区间），结束键不包含（开区间），省略任一界值表示该侧无界；省略数量上限表示不限制，传 0 时即使有匹配也返回空集。结果先按 Unicode 码点升序排列，再在排序后的序列上施加 `[start_key, end_key)` 窗口并截取前 limit 项，因此 limit 始终表示窗口内排序最靠前的若干项。每项只含 `key` 和 `value` 两个字段，value 及嵌套对象都是独立深拷贝，调用方修改结果不影响存储、后续扫描或重新打开的实例；没有匹配项、日志不存在或日志为空时返回空列表，且不创建任何文件。

参数形式在读日志之前全部校验完毕：start_key、end_key 必须是字符串或省略，二者同时给出且 start_key 大于 end_key（含起止键顺序倒置）时抛出 ValueError；limit 必须是非布尔的非负整数或省略，布尔值、浮点数、负数或其他类型统一抛出 ValueError，拒绝调用不读取、创建、截断或追加日志。随后按 recover 完全相同的规则完整校验日志（UTF-8、JSON、字段集合、重复字段、序号连续性及 JSON 值），提交区域、已结束的未提交记录或不可识别尾部中的任何非法内容都统一抛出 WalCorruptionError，绝不返回部分结果；能够识别为一次未完成写入的尾片（未完成 JSON 前缀、终止符未落盘的完整记录、截断的 UTF-8 字节）按 recover 规则忽略。扫描只能看到最后一次完整 commit 的内容：未提交 set/delete 与未完成尾片一律不可见。

scan 是纯只读入口：不截断、不追加、不改写日志，不改变公开的 state、commit_seq、pending_count，也不改变后续 append 依赖的已接受前缀边界（观测性重放后恢复缓存的边界，与 audit、pending_changes 一致）；重复扫描同一可接受日志前缀以及重新打开实例后得到完全相同的序列。关闭实例调用 scan 抛出 WalClosedError（优先于参数校验）；readonly 实例可以扫描且全程不获取写租约，可在存活的 exclusive 写实例旁打开并读取；exclusive 实例的扫描不释放也不改变其已有租约，扫描后仍可继续写入。扫描结束后 set、delete、commit、rollback、apply_batch、restore、repair_tail 及 recover、get、contains、snapshot、history、pending_changes、audit 均按原有规则工作，异常优先级、深拷贝与崩溃恢复行为保持不变。

`restore(target_seq)` 提供把已提交历史快照写回为新的当前状态的入口，供单写者安全回到已知版本，且不改变 set、delete、commit、rollback、recover、snapshot、history 等既有入口的结果、不重写任何旧记录。target_seq 必须是非布尔的非负整数且不超过调用时的最新 commit_seq，类型错误、负数或越界统一抛出 ValueError。调用先按 recover 和 snapshot 的完整规则校验日志（UTF-8、JSON、字段集合、重复字段、序号连续性、终止符与 JSON 值），任何损坏仍抛出 WalCorruptionError；若存在已完整写入（带终止符）但未提交的 set/delete，或可被 recover、audit 识别的尾部未完成片段，则抛出新增的 `WalPendingError`，文件、state 和 commit_seq 均保持原样，调用方须先 commit、rollback 或 repair_tail。校验通过后，restore 读取目标提交状态，将当前状态与目标状态的键集合合并，按 Unicode（码位）键顺序逐个写入差异：目标有而当前没有，或两者都有但值不同的键写 set，当前有而目标缺失的键写 delete；值比较区分 JSON 类型（1 与 true、嵌套结构中的数字与布尔都不视为相同），随后写入一个新的 commit。目标与当前完全相同也会写入空变更批次并只推进一次序号，restore(0) 表示恢复为空对象，空日志同样从序号 1 开始遵守该规则。成功返回新 commit_seq；state 等于目标状态且为独立深拷贝，pending_count 为零，snapshot、history 以及重新打开后的恢复结果都显示相同的新状态和序号，旧提交内容保持不变、可继续按旧序号查询。restore 沿用现有日志结构、记录顺序和每条记录的持久化要求（逐条写入、flush、fsync）；变更或 commit 在写入或 fsync 时发生 OSError 直接传播，旧的已提交 state 与 commit_seq 不得提前改变，此前已成功写入但尚未提交的记录留在 pending_changes 中，可由 rollback 按既有规则清除。在完成参数和日志校验前不截断尾片、不追加字节；exclusive 写租约、WalClosedError 和深拷贝约定同样适用，其他公开方法及既有日志的兼容读取行为不变。

`apply_batch(base_seq, changes)` 提供原子批量提交入口：调用方一次提交一组按给定顺序执行的 set/delete 修改，每条修改先写入日志，最后以一个新的 commit 记录（序号为最新提交序号 + 1）封口，效果与逐条调用 set/delete 再 commit 完全一致。base_seq 是调用方声明的基准提交序号（乐观并发比较前提），必须是非布尔的非负整数；changes 必须是有序的变更列表（或元组），每项只能是现有记录语义——set 项恰好含 op、key、value，delete 项恰好含 op、key，键为字符串、值遵循现有 JSON 兼容规则；空集合表示空提交（只写一条 commit、序号推进一次）。参数形式不合法统一抛出 ValueError，且全部参数校验先于任何日志动作完成。随后按 recover 的完整规则校验日志，任何损坏仍只抛出 WalCorruptionError；存在已完整写入但未提交的 set/delete 记录或可识别的未完成尾片段时抛出 WalPendingError（与 restore 同一"日志必须已封口"规则）；基准序号与当前已提交序号不一致时抛出新增的 `WalConflictError`。这些拒绝都不写入、不截断文件、不改变内存状态；只读实例与已关闭实例分别优先抛出 WalReadOnlyError、WalClosedError。写入阶段沿用单写者租约、逐条 flush+fsync 与序号单调规则：任一变更记录或最终 commit 在持久化前失败都直接传播原始 OSError，已落盘但未封口的前缀只能通过 pending_changes 观察并可由 rollback 清除，内存 state 与 commit_seq 不前进；进程在任一写入边界终止后重开，恰好恢复到最近一次完整提交，批量中未封口的部分绝不应用。成功后返回新的 commit_seq，state、snapshot、history 与重新打开后的 recover 都与逐项重放一致；写入记录时对值做深拷贝，调用方的变更集合及嵌套对象与存储互不共享。旧入口行为、旧日志兼容读取、别名路径租约、深拷贝约定与损坏日志拒绝规则均保持不变。

`key_version(key)` 提供按键查询版本的只读入口，是乐观条件写入的读侧：返回该键最近一次完整提交中被 set 或 delete 的提交序号——从未出现在任何已提交批次中的键返回 0，被删除的键保留最后一次删除所在的提交序号，之后未触碰该键的提交不会改变它。它只观察最后一次完整提交：已完整写入但未提交的 set/delete 记录和可丢弃的末尾片段都不可见，因此返回的版本始终对应调用方实际可读的已提交状态。调用先按 recover 的完整规则校验整个日志：日志不存在或为空返回 0 且不创建任何文件，任何损坏统一抛出 WalCorruptionError 且不返回部分结果；已关闭实例优先抛出 WalClosedError（先于键校验），非字符串 key 抛出 ValueError 且在读取日志之前。该查询不追加、截断或改写日志，不改变 state、commit_seq、pending_count 或后续 append 依赖的已接受前缀边界（观测性重放后恢复缓存的边界，与 scan、diff、pending_changes 一致）；对同一可接受日志前缀重复调用以及重新打开实例后结果一致，readonly 实例无需写租约即可调用。

`set_if_version(key, expected_seq, value)` 与 `delete_if_version(key, expected_seq)` 提供按键版本的乐观条件写入入口，供单写者在提交前确认自己看到的键仍是同一历史状态：调用方以 expected_seq 声明此前通过 key_version 观察到的键版本，仅当该键在最新完整提交中的版本仍等于 expected_seq 时才写入一条 set 或 delete 记录并紧接一条新的 commit 记录——效果与先调用 set/delete 再 commit 完全一致，成功返回新的 commit_seq，state、recover、snapshot、history、diff、scan、pending_changes 与 key_version 随即反映同一已提交结果。expected_seq 必须是非布尔的非负整数：0 要求该键从未出现在任何已提交批次中，更大的值要求该键最后一次已提交的 set 或 delete 恰好携带该提交序号；key 必须是字符串，value 遵循现有 JSON 兼容规则并深拷贝写入记录。所有参数错误统一抛出 ValueError 且先于任何日志动作完成；已关闭实例抛出 WalClosedError、只读实例抛出 WalReadOnlyError，优先级与既有写入口一致。随后按 recover 的完整规则校验日志，任何损坏仍只抛出 WalCorruptionError；存在已完整写入但未提交的 set/delete 记录或可识别的未完成尾片时抛出 WalPendingError（与 restore、apply_batch 同一"日志必须已封口"规则）；键版本与 expected_seq 不符时抛出 WalConflictError，冲突判断始终针对最新完整提交。这些拒绝都不写入、不截断文件、不改变内存状态。写入阶段沿用单写者租约、逐条 flush+fsync 与序号单调规则：任一记录在持久化前失败都直接传播原始 OSError，已落盘但未封口的记录只出现在 pending_changes 中并可由 rollback 清除，内存 state 与 commit_seq 不前进；进程在任一写入边界终止后重开，恰好恢复到此前最近一次完整提交。旧入口行为、完整性链、别名租约、损坏日志拒绝与旧格式日志的兼容读取均保持不变。

`apply_if_versions(expected_versions, changes)` 把按键版本的乐观条件写入推广到一次保护多个键的原子批量提交：expected_versions 是键到版本号的字典，版本号沿用 key_version 规则（从未被任何已提交批次触碰的键为 0，被删除的键保留删除所在提交的序号），仅当映射中每个键在校验开始时的最新完整提交里的版本仍等于声明值时，changes 才按给定顺序逐条写入并以一个新的 commit 记录（序号为最新提交序号 + 1）封口——效果与 apply_batch 完全一致，成功返回新的 commit_seq，state、recover、snapshot、history、diff、scan、key_version 及重开结果随即反映完整批次。expected_versions 必须是字典，键必须是字符串，值必须是非布尔的非负整数；changes 只能是列表或元组，每项只能是恰好含 op、key、value 的 set 项或恰好含 op、key 的 delete 项，值遵循现有 JSON 兼容校验并深拷贝写入记录；同一键可在 changes 中出现多次并依次作用于本批次状态，changes 触及的每个键都必须在映射中出现，映射也可额外包含只用于校验的键；空 changes 仍写一条空 commit 并推进一次序号。所有参数错误统一抛出 ValueError，且在读取或创建日志之前抛出；已关闭实例抛出 WalClosedError、只读实例抛出 WalReadOnlyError，优先级与既有写入口一致。随后按 recover 的完整规则校验日志，任何损坏仍只抛出 WalCorruptionError；存在已完整写入但未提交的 set/delete 记录或可识别的未完成尾片时抛出 WalPendingError（与 restore、apply_batch 同一"日志必须已封口"规则）；任一键版本不符时抛出 WalConflictError，版本比较始终针对校验开始时的最新完整提交。这些拒绝都不写入、不截断文件、不改变内存状态，也不消耗序号。写入阶段沿用单写者租约、逐条 flush+fsync 与序号单调规则：任一变更记录或最终 commit 在持久化前失败都直接传播原始 OSError，已落盘但未封口的前缀只出现在 pending_changes 中并可由 rollback 清除，内存 state 与 commit_seq 不前进；进程在任一写入边界终止后重开，恰好恢复到最近一次完整提交，批量中未封口的部分绝不应用。旧入口行为、完整性链、别名租约、损坏日志拒绝与旧格式日志的兼容读取均保持不变。

`commit_if_seq(expected_seq)` 提供按最近提交序号的原子条件提交入口，把已落盘但未提交的当前批次按调用方声明的基准序号封口：仅当日志的最新完整提交序号仍等于 expected_seq 时，才追加一条新的 commit 记录（序号为最新提交序号 + 1），把最后一次完整 commit 之后已完整写入（带终止符）的 set/delete 记录按日志顺序一次性提交——效果与此时调用 commit() 完全一致；没有待处理记录时同样只写一条空 commit、序号推进一次。成功返回新的 commit_seq，state、recover、snapshot、history、diff、scan、pending_changes、key_version 及重新打开后的恢复结果随即反映同一已提交结果。expected_seq 必须是非布尔的非负整数，参数错误在读取或创建日志之前抛出 ValueError；已关闭实例优先抛出 WalClosedError，只读实例优先抛出 WalReadOnlyError，优先级与既有写入口一致。随后按 recover 的完整规则校验日志，非法 UTF-8、非标准 JSON 常量、重复字段、字段集合或序号错误统一抛出 WalCorruptionError；存在可识别的未完成尾片时抛出 WalPendingError，要求先 repair_tail，文件、内存状态、序号与完整待处理记录均不变（完整待处理记录本身正是本入口要封口的内容，不视为拒绝理由）；最新提交序号不等于 expected_seq 时抛出 WalConflictError，比较始终针对最新完整提交。这些拒绝都不写入、不截断文件、不改变内存状态，也不消耗序号。写入阶段沿用单写者租约、逐条 flush+fsync 与序号单调规则：修改记录已落盘而 commit 写入或持久化失败时原样传播 OSError，已提交 state 与 commit_seq 不前进，残留记录可由 pending_changes 观察并由 rollback 清除；进程在任意写入边界终止后重开，恰好恢复到最近一次完整提交且不跳号。成功调用不改写旧日志字节，也不改变既有写入、恢复、审计和查询入口的行为；普通、readonly、exclusive、完整性保护及旧格式日志继续兼容。

`WalStore(path, exclusive=True)` 在打开时为该日志路径申请独占写入租约，租约在实例存活期间覆盖 set、delete、commit、commit_if_seq、rollback、restore、apply_batch、set_if_version、delete_if_version、apply_if_versions 与 repair_tail，供部署明确落实单写者约束。租约实现为对规范化绝对路径派生的旁路锁文件的 flock：同一日志路径的所有拼写竞争同一把锁，锁按打开文件描述生效（同进程内两个独占实例同样互斥），进程异常终止时内核自动释放，不会留下阻塞后续打开的失效状态。租约参数不是布尔值时抛出 ValueError；相同规范化路径已有独占租约时，新的独占实例在读取日志前抛出唯一的 WalBusyError，不创建、截断或追加日志，也不影响已有实例的 state 与 commit_seq，且冲突结果可重复观察。`exclusive=False` 或省略时行为与现有默认完全一致，查询类方法保持只读。`close()` 释放租约并可重复调用，实例也支持 `with` 上下文管理自动释放；关闭后再调用除 close 外的任一公开方法都抛出唯一的 WalClosedError。成功关闭后再次以 exclusive=True 打开同一路径，按原有规则恢复最后一次提交，state、commit_seq、snapshot、history、audit、pending_changes 与 repair_tail 的结果均不受影响。独占模式不改写 WAL 记录结构或提交顺序，写入与 fsync 失败仍沿用现有 OSError 语义且内存状态不变。

租约身份按日志的实际对象（`st_dev`、`st_ino`）确定，而不只按路径字符串：指向同一实际日志的符号链接（含多级链接与经链接目录的别名）、硬链接以及规范化后相同的路径都竞争同一把租约，因此同一实际 WAL 不可能同时存在两个独占写者。对已存在的日志，打开时沿符号链接取实际对象的身份并对以（设备、inode）命名的共享旁路锁文件加 flock，同时持有一个指向该对象的只读描述符固定身份；每次写模式打开（set/delete 追加、rollback 与 repair_tail 的就地截断）都校验句柄身份确为租约对象，路径在租约期间被替换成另一对象时写入以 OSError（ESTALE）中止，绝不改写非租约日志。日志尚不存在时，以“最长存在祖先解析符号链接、其余不存在分量原样拼接”得到的规范目标路径命名一把“首次创建”串行锁；并发首次打开时只有一个实例取得该锁，其余别名实例在重新解析后发现对象已存在或正在被创建，转而竞争该 inode 租约并得到 WalBusyError——包括悬挂符号链接两端、经不存在目录的一致拼写以及跨进程同时打开。取得首次创建锁的一方在首次真正写日志（`_append` 创建文件）时原子地取得新 inode 的租约、固定对象后再释放创建锁；若该方一直未写就在 `close()` 释放，创建锁随之释放，不留下阻塞状态，且全程不创建日志本身。以上别名判定均在全部参数校验通过之后、任何 WAL 内容读取或持久化动作之前完成；冲突方在读取日志前即收到唯一的 WalBusyError，不会得到自己的独占状态，也不改变持有方的 state、commit_seq 或文件字节。符号链接环路等身份无法解析的情形与底层文件操作失败一律沿用对应 OSError，不伪装成成功写入或序号推进；非独占与只读实例不申请任何身份或创建锁，旧 WAL 的兼容读取、日志格式、提交顺序、未提交记录与损坏日志拒绝规则均保持不变。


`WalStore(path, readonly=True)` 以只读模式打开日志，把恢复、审计与查询与单写者部署明确分离。`readonly` 参数必须是布尔值，否则抛出 ValueError；`readonly=True` 与 `exclusive=True` 同时给出时统一抛出 ValueError，且所有参数校验失败前绝不读取、创建或改写任何路径（不创建 WAL 或锁文件）。只读实例打开时按现有 recover 规则解析日志，公开的 state、commit_seq，recover 的 pending_count，以及 snapshot、history、pending_changes、audit 的结果与普通实例完全一致；不存在或空日志仍表示空状态且不创建任何文件，末尾未完成片段继续遵循既有丢弃与审计口径，任何超出可接受边界的内容仍抛出 WalCorruptionError。只读实例的 set、delete、commit、commit_if_seq、rollback、restore、apply_batch、set_if_version、delete_if_version、apply_if_versions 与 repair_tail 一律抛出新增的 `WalReadOnlyError`，异常发生前不截断尾片、不追加记录、不推进序号、不改变内存状态；即使日志已有完整未提交记录，也保留原字节并继续由查询入口按既有规则观察。只读实例不申请写租约，可以在一个 exclusive 写实例存活时打开并读取同一路径，多个只读实例也可并存。关闭后的实例仍优先抛出 WalClosedError，`close()` 与 `with` 上下文管理保持幂等。`readonly=False` 或省略 `readonly` 时行为与现有默认完全一致，既有 WAL 格式、深拷贝约定、损坏日志拒绝与所有成功写入行为均保持兼容。

`WalStore(path, integrity=True)` 为日志启用完整性保护模式：受保护日志的每条记录（set、delete、commit）都额外携带一个 `ic` 完整性字段，其值是把该记录的规范核心内容（除 `ic` 外的全部字段，含提交序号 seq，按排序键 JSON 序列化）链接到前一条记录摘要上的 SHA-256 链式摘要，首条记录链接到固定的域分离种子。链式结构同时覆盖记录内容、操作顺序和提交序号：改写任何记录的内容、删除或插入记录、重排记录顺序都会使首个被触动边界之后的摘要校验失败。`integrity` 参数必须是布尔值，否则抛出 ValueError；省略或为 False 时行为与既有默认完全一致——旧格式日志继续按原有格式读写，不新增任何字段。

格式由日志自身决定：重放时第一条被解析的记录确定整个日志是否受保护，之后的每条记录必须与其一致，受保护与未保护记录混用一律抛出 WalCorruptionError。`integrity=True` 用于新建日志（不存在或空日志直接从首条记录开始受保护链）或已经受保护的日志；用它打开非空且完全未受保护的旧日志时抛出唯一的 `WalIntegrityError`，不创建、截断、追加日志，也不改变任何内存状态，调用方须改用默认模式打开（保持旧格式）或另建受保护日志。受保护日志由默认模式打开时同样识别其格式：继续校验完整性并以受保护格式追加，绝不降级为未保护记录。

打开以及 recover、audit、pending_changes、snapshot、history、diff、scan、key_version 和任一写入口（set、delete、commit、commit_if_seq、rollback、restore、apply_batch、set_if_version、delete_if_version、apply_if_versions、repair_tail）在产生结果前都按 recover 的完整规则重放并验证整个日志的完整性链；受保护日志中校验缺失、摘要不匹配或非法混用统一抛出 WalCorruptionError，不返回部分结果，不自动修复，也不改变 state、commit_seq、pending_count、文件大小或后续 append 依赖的边界。repair_tail 仍然只能清除可识别的末尾未完成片段——受保护日志中该片段本身必须是完整性校验通过的完整记录（或无法解析的中断写入前缀），完整性不匹配永远按损坏处理，绝不截断。受保护模式沿用单写者预写日志的持久化路径：每条修改和 commit 仍逐条写入、flush、fsync，确认提交边界后才推进内存提交状态；写入或同步发生 OSError、进程在记录或提交边界终止时，重新打开恰好恢复最后一次完整提交，未封口修改只出现在 pending_changes（不暴露 `ic` 字段），重试不跳号且链状态与日志一致。成功提交后的完整性元数据在 snapshot、history、diff、scan 和重新打开的 recover 中保持一致，返回值仍为独立深拷贝，调用方修改不影响存储。readonly=True 与 integrity=True 可组合，只读实例照常验证和查询但不能写入；exclusive 租约继续覆盖所有变更入口，integrity 打开失败（含 WalIntegrityError）不会残留租约。所有既有 API、返回字段、序号规则、别名租约、异常优先级与合法旧 WAL 的兼容读取均保持不变。

`WalStore(path, strict_tail=True)` 启用可选的严格尾片恢复策略：默认策略在重放时静默丢弃 recover 规则可识别的单个末尾未完成片段（截断 UTF-8、未完成 JSON 前缀或无终止符的完整记录），严格策略则在完整校验通过后把该片段视为硬错误，抛出新增的 `WalTailError`。`strict_tail` 只接受布尔值，省略或传 False（含位置参数）时全部既有行为——recover、查询、提交、回滚、批量、历史、租约与 integrity 模式的结果、序号、深拷贝和崩溃恢复——逐字节、逐序号保持不变；非布尔参数与其他参数一样在读取、创建日志或申请租约之前抛出 ValueError。日志不存在、为空或没有尾片时严格构造照常返回实例；已经完整写入（带终止符）但未提交的 set/delete 记录仍是 pending，可正常 commit 或 rollback，绝不被当作尾片拒绝。

严格构造仍先完整执行 UTF-8、JSON、重复字段、字段集合、序号连续性、键值类型与 integrity 链的全部既有校验：任何损坏仍优先抛出 WalCorruptionError（包括受保护日志中完整性不匹配的无终止符片段），integrity=True 打开非空旧格式日志仍优先抛出 WalIntegrityError，这两类拒绝都先于 WalTailError。仅在全部校验通过、且可接受前缀之后确实存在 recover/audit 可识别的末尾片段时才抛出 WalTailError，错误公开 `valid_bytes`（与 audit 的 valid_bytes 一致）、`tail_bytes`（原始尾片字节数）与 `tail_kind`，后者仅可为 `"truncated_utf8"`（片段末尾是被截断的多字节 UTF-8 序列）、`"incomplete_json"`（未完成的 JSON 前缀）或 `"missing_terminator"`（一条通过全部结构、字段、序号与完整性校验的完整记录，但其终止符未落盘）；同一尾片同时含截断 UTF-8 与未完成 JSON 时优先标为 `"truncated_utf8"`。抛出 WalTailError 时绝不采纳候选 state 或 commit_seq，不截断、不追加、不创建日志，strict_tail=True 与 exclusive=True 组合时构造失败会像其他打开失败一样释放全部租约描述符，不留下 exclusive 租约。

严格实例存活期间，所有会重放日志的读写入口——recover、get、contains、key_version、scan、snapshot、history、diff、pending_changes 以及 set、delete、commit、commit_if_seq、rollback、restore、apply_batch、set_if_version、delete_if_version、apply_if_versions——一旦发现带外出现的尾片同样抛出 WalTailError（且不静默截掉），状态、序号、pending_count 与文件字节均保持不变；关闭实例仍优先 WalClosedError、只读实例的变更入口仍优先 WalReadOnlyError。`audit()` 不采用严格策略，继续按既有口径报告 valid_bytes、committed_bytes 与 tail_bytes；`repair_tail()` 同样不采用严格策略，是严格模式下明确的运维出口：它继续只把可识别尾片就地截到 valid_bytes（合法前缀字节与完整 pending 记录不动），清理成功并持久化后，严格实例（及重新以 strict_tail=True 打开的实例）立即恢复正常读写。严格策略对旧格式、受保护（integrity）、readonly 与 exclusive 实例同样适用，对同一日志前缀的重复严格打开结果一致；除 repair_tail() 明确截去尾片外，任何严格拒绝都不改写合法字节、不改变 pending_count，也不消耗序号。
